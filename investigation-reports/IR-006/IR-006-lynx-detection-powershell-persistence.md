## 1. Summary

On 16/05/2026 I ran a five-stage attack simulation on the Windows 10
endpoint DESKTOP-MM1REM9: host discovery, payload retrieval via
PowerShell HTTP, LOLBin execution (blocked by AppControl), encoded
PowerShell execution, and persistence via a registry run key and a
scheduled task.

Lynx normalized the upstream Sysmon and Elastic detections into one case:
26 behaviors across a 30-minute window, HIGH severity, risk score 5,109,
three tactic categories (EXECUTION, PERSISTENCE, DISCOVERY).

The cross-layer check confirmed 6 Suricata network events from the
independent NDR pipeline corroborating the PowerShell HTTP activity the
EDR saw. Three repeated GET requests to /payload.txt on 10.0.30.10:8080
were recorded by both sensors. Same IPs, same timestamps, two pipelines
with no shared data path. Dual-source confirmation.

**Assessment:** Early-stage post-compromise behavior, the kind seen right
before payload deployment or persistence. No credential access, no
lateral movement, no exfiltration. Persistence confirmed through the
scheduled task and the registry run key.

### 4.2 Process Tree Analysis

The process tree rendered the full execution chain rooted at
powershell.exe (pid 9160). All discovery binaries appear as direct
children. net1.exe appears as a grandchild of net.exe.

**Observed process chain:**

```
powershell.exe (pid 9160) - C:\Windows\System32\WindowsPowerShell\v1.0\   [EXECUTION]
├── whoami.exe       (pid 38324)    C:\Windows\system32\                   [DISCOVERY]
├── HOSTNAME.EXE     (pid 11856)    C:\Windows\system32\                   [DISCOVERY]
├── ipconfig.exe     (pid 10624)    C:\Windows\system32\                   [DISCOVERY]
├── NETSTAT.EXE      (pid 10076)    C:\Windows\system32\                   [DISCOVERY]
├── net.exe          (pid 7500)     C:\Windows\system32\                   [DISCOVERY]
│   └── net1.exe     (pid 9052)     C:\Windows\system32\                   [OTHER]
└── systeminfo.exe   (pid 7048)     C:\Windows\system32\                   [DISCOVERY]
```

**net1.exe handling:** net1.exe appeared in the raw Sysmon EID 1
telemetry and was rendered as an "Other process" node. No behavior record
matched it and it got no risk contribution. That is correct: net1.exe is
an internal subprocess spawned by net.exe and is not independently
malicious. Its presence in the tree confirms telemetry fidelity without
inflating the case score.

### 4.3 Cross-Layer Corroboration

I queried the NDR pipeline for Suricata events matching the victim IP
within a 15-minute window around the detected behaviors. Six events came
back, corroborating the EDR-observed PowerShell HTTP activity from an
independent sensor.

**Corroboration summary:**

| Field | Value |
|---|---|
| Network events returned | 6 |
| Suricata alerts triggered | 0 |
| Event types | http, fileinfo |
| Victim IP | 10.0.20.10 |
| Remote IP:port | 10.0.30.10:8080 |
| URI | /payload.txt |
| HTTP status | 200 |
| Successful requests | 3 |
| User-Agent | Mozilla/5.0 (Windows NT; Windows NT 10.0; en-US) WindowsPowerShell/5.1.19041.6456 |

**Assessment:** Three repeated PowerShell HTTP retrievals to one
destination on a non-standard port (8080), confirmed by both pipelines.
The EDR and NDR sensors share no data path: the Elastic Agent on the
victim and Filebeat on pfSense collect independently and write to
separate index patterns. Matching events on the same IPs and timestamps
is dual-source confirmation.

Zero Suricata alerts. The 6 events are flow records, not alerts. Suricata
saw the traffic but had no rule for PowerShell HTTP to an internal host
on port 8080. Detection gap, addressed in Section 8.

## 7. Containment Considerations

Controlled simulation. If the activity had been unauthorized, the actions
would be:

- Isolate the host from the network pending scope assessment
- Remove the scheduled task created at stage 5
- Delete the Run key persistence entry
- Locate and remove any file written during the payload retrieval stage
- Review outbound connections to 10.0.30.10 across the environment for
  other affected hosts
- Confirm no secondary payload ran after the 3x retrieval
- Reset credentials for the active user session if the privilege context
  is uncertain

## 8. Detection Gaps

### Gap 1: No Suricata alert for PowerShell HTTP to an internal host on a non-standard port

Six Suricata flow events recorded, zero alerts. No rule covers internal
HTTP traffic to the attack subnet on port 8080.

**Fix:**

```
alert http 10.0.20.0/24 any -> 10.0.30.0/24 8080 (msg:"INTERNAL HTTP to attack subnet port 8080"; sid:9000003; rev:1;)
```

Broader coverage:

```
alert http 10.0.20.0/24 any -> 10.0.30.0/24 !80 (msg:"INTERNAL HTTP to attack subnet non-standard port"; sid:9000004; rev:1;)
```

### Gap 2: PowerShell User-Agent not alerted

The User-Agent WindowsPowerShell/5.1.19041.6456 is a reliable indicator
of PowerShell HTTP activity. No Suricata rule matched it.

**Fix:**

```
alert http 10.0.20.0/24 any -> any any (msg:"PowerShell User-Agent in HTTP traffic"; content:"WindowsPowerShell"; http_header; sid:9000005; rev:1;)
```

### Gap 3: AppControl block not captured in telemetry

AppControl blocked certutil.exe but no event from the EDR pipeline
confirmed the block. If AppControl were disabled, the certutil execution
would proceed with no detection at all.

**Fix:** Enable AppLocker or WDAC operational log collection. The
relevant Windows event channel is Microsoft-Windows-AppLocker/EXE and
DLL. Also add a Sysmon EID 3 detection profile for certutil making
outbound connections to non-Microsoft destinations, which catches the
network attempt whether or not the execution block is logged.

### Gap 4: rundll32.exe outbound connections unresolved

The hunt showed rundll32.exe with 3 outbound connections to one IP. Not
part of the planned scenario, and the destination IP was not verified
during this session.

**Follow-up:** Pull EID 3 events for rundll32.exe in the case window,
confirm the destination IP, and compare against known Windows or CDN
ranges. Outside those ranges, treat it as a secondary lead and widen the
investigation.
